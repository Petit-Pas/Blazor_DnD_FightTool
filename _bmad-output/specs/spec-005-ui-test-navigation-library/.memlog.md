- (note) Input: in-chat brief from Benoit - a library to navigate UI for unit tests, reusable by agents writing throwaway code, ending in screenshots proving a feature works; plus skills/agents to maintain it, written only after architecture is agreed.
- (note) Brownfield: no bUnit and no Playwright exist today; tests/UI/FightBlazorComponentsTests is plain NUnit over non-render logic (log token parsing). src/Analyzers/DnDFightTool.Analyzers exists (netstandard2.0, Roslyn 4.8) and is the natural home for a new analyzer.
- (decision) Rendering engine is Playwright driving the DndUi.Web ASP.NET Core host, and only that. bUnit rejected: it cannot produce real screenshots, and MudBlazor 9 dialogs/popovers need hand-stubbed JSInterop, which is exactly the surface in scope.
- (decision) Scenarios run under NUnit via dotnet test, same runner and CI path as every other test project, despite being integration-shaped rather than unit-shaped.
- (constraint) The fixture must start real Kestrel on a dynamic port. WebApplicationFactory default TestServer is an in-memory transport with no socket, so Playwright cannot reach it.
- (decision) Navigation API is typed fluent page objects, so IntelliSense is the discovery mechanism for both humans and agents.
- (decision) Agent consumption is a scratch NUnit test project the agent writes into and runs with dotnet test, reading assertion output and screenshots. Rejected: dotnet-script REPL, YAML CLI runner, MCP server - each adds a toolchain or reinvents a scripting language.
- (decision) Screenshots are saved to a folder as evidence artifacts the agent attaches to its report. No baseline image diffing.
- (decision) Enforcement is Roslyn mechanism B only: an analyzer requiring every routable @page component to have a corresponding page object, catching newly added pages. Benoit: B for good measure.
- (decision) Roslyn mechanism A (source generator emitting UiIds constants from .razor) rejected. Benoit: proper scenarios already fail when the UI degrades, so a compile-time selector catalog is redundant weight.
- (decision) Roslyn mechanism C (analyzer requiring data-testid on interactive components) rejected as fragile and noisy.
- (constraint) No blanket data-testid campaign across production .razor markup. Dropping mechanisms A and C removed the need. Locators use Playwright role and text semantics.
- (decision) The .razor-scoped Copilot instructions file is updated so UI changes trigger page-object updates, complementing the analyzer.
- (decision) Scenarios reach app state by driving the real UI, not by a seeding endpoint or DI override. Benoit: one test checks a goblin can be created, another that it can be added to a fight, and so on - the steps compose.
- (constraint) No test-only backdoor, seeding endpoint, or DI override may be added to the production host.
- (decision) Initial coverage is all existing pages and dialogs, not a vertical slice.
- (decision) Three ordered deliverables: (1) the navigation library, (2) the Roslyn analyzer, (3) the skills, agents, and instructions. Deliverable 3 is written only after 1 and 2 are agreed, so it captures final decisions.
- (note) Assumption: Chromium only; no cross-browser matrix.
- (note) Surface inventory: 5 routable pages (CharacterListEditorPage, FightDashboardPage, FightersPage, CharacterEditorPage, AttackEditorPage); dialog surfaces are the 4 DnDQueryPrompter modals, InitiativeInputDialog, and RollableDialogBase.
- (constraint) Determinism is achieved through the UI, not a backdoor: DiceRollResultInputComponent exposes roll results as an editable MudNumericField inside the query modals, so a scenario types the exact roll it wants. This is what makes the no-backdoor constraint viable.

- (event) Self-validate pass 2 (preservation): PASS. Every load-bearing claim from the brief and both question rounds landed. Wrapper-only drops: the bUnit-vs-Playwright comparison table and the full Roslyn A/B/C explanation, retained as rationale in the memlog and partially in deliverables.md.
- (event) SPEC.md and deliverables.md derived and written. 9 capabilities, 1 spec-authored companion, 1 adopted companion (project-context.md), 6 assumptions, 7 open questions.
- (decision) The library and the agent scratch project live under a new top-level /uitests folder, consumed by project reference only, not packaged.
- (decision) State isolation is a combination: Reset() is added only where it is a legitimate business operation the app could itself expose (IFightContext, and likely ICombatTurnService, IDnDLogService, IAppliedStatusRepository). Test convenience alone never justifies a Reset. Benoit explicitly excluded ICharacterRepository - wiping saved characters is not a business operation. Everywhere reset is not business-acceptable, scenarios clean up after themselves.
- (decision) Per-scenario host rebuild rejected in favour of the selective-Reset approach above.
- (decision) DndUi.Web inline service registrations are refactored into RegisterWebAppServices(services, dataFolder), called by both Program.cs and the test fixture, matching the existing IoC/ServiceCollectionExtensions convention. This is a production refactor, not a test backdoor.
- (decision) Storage isolation uses a unique temp folder per run with the real LocalFileCharacterRepository; dataFolder is already a constructor argument in Program.cs so no new type or abstraction is needed. Keeps the real persistence path under test.
- (decision) Scratch scenarios are gitignored, never committed, and wiped between runs. The durable evidence is the screenshots the agent reports, not the throwaway code.
- (decision) The page-object coverage analyzer emits a build-breaking error, not a warning.
- (decision) CI integration is out of scope and becomes a non-goal. Benoit: the project runs locally only for now - no CI, no deployment, nothing. Recorded in project-context.md as a standing fact for future runs.

- (decision) CAP-5 building blocks may bypass the UI and call domain services directly. Benoit: creating a default goblin can be done straight on the services. This supersedes the earlier blanket rule that scenarios reach all state by driving the UI.
- (constraint) New split rule: arrangement may bypass the UI, the behaviour under test may not. Every capability reachable through the UI keeps at least one scenario exercising it through the UI, so UI-driven coverage is not quietly lost to convenience.
- (constraint) Direct service arrangement uses the in-process IServiceProvider the fixture already holds; still no seeding endpoint or test-only registration in the production host.
- (constraint) Only host singletons are arrangeable from the test process (IFightContext, ICharacterRepository, ICombatTurnService, IAppliedStatusRepository, IDnDLogService). Per-circuit scoped services (IGlobalEditContext, IDiceRollNotifier, IStateFullNavigation) belong to the browser circuit and are unreachable.
- (constraint) Mutating a singleton after a page has rendered does not repaint it. Arrangement happens before navigation, or fires the same notification the production path fires.
- (event) SPEC.md and deliverables.md re-derived for the CAP-5 change. Coherence and preservation both PASS.
- (decision) Open questions 1 and 2 resolved: no Reset() is added to any service. Scenario teardown undoes every command via a UndoLastCommandAsync loop while HistoryLength > 0, returning all command-driven state (fight, turns, log, statuses) to empty. Benoit proposed this and noted it doubles as a test that undo genuinely restores everything.
- (constraint) The undo-everything teardown asserts the resulting state is empty, so a broken undo fails the scenario that caused it rather than silently corrupting later scenarios.
- (note) Finding: character persistence is NOT command-driven. ICharacterRepository is used directly by CharacterEditorPage, CharacterListEditorPage and GlobalEditContext; only AddToFight handlers go through commands. Undo therefore cannot clean up created characters - the two cleanup mechanisms split along that seam.
- (decision) Open question 3 resolved: the temp folder stays per-run, not per-scenario (per-scenario would require the rejected host rebuild, since the repository singleton takes dataFolder at host-build time). Teardown instead deletes every character via the existing ICharacterRepository.GetAllCharacters + Delete business API. No new API, no Reset.
- (constraint) Caveat: UndoableMediator defaults to CommandHistoryMaxSize 64. A scenario exceeding 64 top-level commands loses the oldest from history and cannot fully undo, leaving residue. The test host composition raises the limit, or scenarios stay short.
- (constraint) Caveat: after a full undo the redo stack holds the undone commands (RedoHistoryMaxSize 32). State is clean, but a scenario asserting on undo/redo button availability at its very start would see a stale redo. The first new command clears the redo stack.
- (constraint) Scenarios whose subject is undo/redo itself opt out of the undo-everything teardown.
- (event) SPEC.md and deliverables.md re-derived. Open Questions section removed - all three resolved, zero remaining. Reset() constraints replaced by the undo-everything plus repository-delete teardown. CAP-10 success now requires teardown to prove the slate is clean.

- (decision) The test host composition sets CommandHistoryMaxSize to 1000 (production default 64) so no realistic scenario overflows the history and leaves state teardown cannot undo. Supersedes the earlier keep-scenarios-short mitigation.
